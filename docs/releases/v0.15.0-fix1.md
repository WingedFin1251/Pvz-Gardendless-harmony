本次是 **0.15.0 的修正版（fix1）**：针对"闲置一会儿刷新率掉到 60Hz"，给壳层加了**期望刷新率声明**与一个设置面板。

## 1. 新增：壳层设置面板（长按 GP 按钮打开）

**怎么打开**：先点一下右下角的 **GP 按钮**把它唤出来（它闲置几秒后会贴边半隐），**再长按一下它** → 就会弹出设置面板。

面板里可以设置：

- **画面**：铺满 / 按比例留边（可在设置中设置）
- **期望刷新率**：关闭 / 60 / 120 / 最高 —— 选完**立即生效**，并记住到下次启动
- 面板里还只读显示 **当前屏幕刷新率 / 期望值 / 是否生效**、屏幕支持的档位，以及**实测引擎帧数**（打开期间每秒刷新）

> 这一项是向鸿蒙**控帧系统**声明"本页面期望的帧率"，**不是锁帧**：系统在无触摸、内容静止时仍可能自行降档（对应官方 OpenGTX 的 `TOUCH_MODE` 语义）。
> **需要系统配合**：请把「设置 → 显示和亮度 → 屏幕刷新率」设为 **高**。设为"智能"时由系统按场景决定，该声明基本不起作用。
> **机型差异（实测）**：**平板有效**（系统=高时稳定 120Hz）；**手机 BRA-AL00 不被采纳** —— 无论系统设"高"还是"智能"、也无论把声明范围收紧成单值 `{120,120,120}`，无触摸时屏幕都停在 60Hz，只在触摸/操作时由系统自行提频到 120。这属于系统侧策略，应用层无法解决。
> **引擎帧率是另一套设置**：入口在**游戏内右下角"扳手"页面**（24 / 30 / 60 / 无限制）。注意 GP-Next「性能」页的"目标FPS"在选「无限制」时会显示 GP-Next 存档里的旧数字（例如 60），**不可信**；请以壳层面板里的「**实测**」为准。
> **不建议**开启 GP-Next「实验性 → 实验帧率调度」：它是上游的实验能力（用纯 JS 节拍器接管帧循环），在平板上会造成**明显卡顿**。

## 2. 期望刷新率声明（displaySync）

壳层用 `displaySync.setExpectedFrameRateRange()` 参与整机刷新率决策，且**只在页面可见时**持有（切后台即释放，避免空刷帧）。

实测（**平板**，系统刷新率=**高**，全程零输入，唯一变量=该声明）：

| 条件 | 90 秒内的显示刷新率 |
| :--- | :--- |
| 声明关闭 | 60Hz × 18（120 占比 0%） |
| 声明开启 | 120Hz × 18（120 占比 100%） |

同法在**手机 BRA-AL00**上实测（各 20 次采样，间隔 2 秒，触摸后等 12 秒）：声明=120 与声明=关闭**都是 60Hz × 20** —— 即该机型不采纳应用的期望帧率声明。（平板把系统档位改成"智能"后同样不生效，改回"高"即恢复。）

## 已知限制

- **通用（base）变体没有悬浮 GP 按钮**，因此它没有上述设置面板，只有内置的期望刷新率声明
- 面板里的「最高」按屏幕支持上限声明；本次仅实测了 60 / 120 两档
- 期望刷新率声明**依赖系统策略**：手机（BRA-AL00）无法通过该声明长期保持 120Hz，仅触摸/操作时由系统提频
- 壳层仍未实现流式 `fs`（`open/read/write/seek/fstat/ftruncate`）与 `dialog|open`；目前负载未触发到
