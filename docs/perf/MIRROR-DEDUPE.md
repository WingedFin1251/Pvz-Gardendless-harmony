# localStorage→原生镜像：去重收益的实测（并纠正报告的一处高估）

> 日期：2026-10-07 ｜ 设备：HUAWEI Mate 60（BRA-AL00 型号）
> 背景：性能审查报告附录 A 把"逐帧 JSB 镜像"列为掉帧**主因**，并据此列出 P0①。

## 做法

`touchPatch.js` 覆写 `localStorage.setItem` 后无条件调 `saveToNative`。现加
`lastMirrored[key] === value` ⇒ **值未变直接 return**，不跨进程、不建 Promise
（ArkTS 侧本来就有 flush 去抖，真正贵的是这次**跨进程搬运**，所以去重必须做在 JS 侧）。

为了**量化**而不是估计，临时加了计数器（每 10 秒用 `console.warn` 打一行），
在"花园"场景里正常操作约 40 秒。测完计数器已撤掉。

## 实测结果（40 秒，6 个统计窗口）

| 时刻 | 白名单 `setItem` | 实际镜像 | 去重挡掉 | 尝试搬运（字符）| 实际搬运（字符）|
| :--- | ---: | ---: | ---: | ---: | ---: |
| 14:34:49 | 87 | 3 | 84 | 9,097,873 | 212,101 |
| 14:34:59 | 51 | 16 | 35 | 5,291,511 | 1,589,106 |
| 14:35:08 | 57 | 0 | 57 | 6,029,631 | 0 |
| 14:35:18 | 70 | 0 | 70 | 7,404,810 | 0 |
| 14:35:28 | 21 | 0 | 21 | 2,221,443 | 0 |
| 14:35:39 | 1 | 0 | 1 | 105,783 | 0 |
| **合计** | **287** | **19** | **268** | **30,151,051** | **1,801,207** |

⇒ **去重挡掉 93.4% 的镜像调用**；跨进程搬运从 **≈30 MB / 40 秒** 降到 **1.8 MB**
⇒ **少搬 ≈28.3 MB / 40 秒 ≈ 708 KB/s**。

（19 次真实镜像集中在最前面两个窗口 = 启动/读档后的状态变化，属正常。）

## ⚠️ 同时纠正报告的一处高估

报告的原文是「花园格子 / 骆驼关的 `update()` 会**逐帧**写存档」，据此推断出主进程多占约 **0.84 个核**。
实测的频率是 **287 / 40 s ≈ 7.2 次/秒**，**不是"逐帧"（≈60 次/秒），高估了约 8 倍**。

这也解释了另一组实测：同一场景（花园、静止 60 秒）下，**整个进程**的 CPU 是

| 构建 | Δ CPU / 60 s | 平均占用 |
| :--- | ---: | ---: |
| 旧（无去重）| 82.14 s | 1.37 个核 |
| 新（有去重）| 77.79 s | 1.30 个核 |

⇒ 差 **−0.07 个核（−7.3%）**，**落在单次采样的噪声带里**，不足以支撑"0.84 个核"的结论
—— 进程 CPU 由**渲染**主导，~700 KB/s 的 JSB 搬运撑不起那个量级。

## 结论

1. ✅ **P0① 是真优化，且已量化**：去掉 **93%** 的镜像调用与 **≈94%** 的跨进程搬运量。
   改动是**严格无损**的（值相同 ⇒ 跳过一次等价写入），并由契约测试 ⑨ 守住。
2. ⚠️ **但报告把"镜像"当作掉帧主因是高估了**。帧率差距的**真正主因仍未找到**；
   报告列为"次因"的 `displaySync` 逐帧刷新率投票、以及渲染本身，都还需要单独验证。
3. 📌 方法论教训：**"每帧"这类描述必须实测计数**，不能从代码结构推断频率
   —— 报告的作者正是因为页内探针看不到应用主进程，才只能靠推断，而推断偏了 8 倍。

# 补正（同日稍晚）：真正的花园里是**逐帧**写，有效手段是"节流合并"而非"去重"

前一节的数据取自**世界地图/关卡**场景（≈7.2～19 次/秒），据此我说报告"逐帧"高估了 8 倍。
**这条要更正**：进到「**真正的花园**」（会不停写存档那个场景）后，实测是：

| 窗口（各 10 秒）| 白名单 `setItem` | 去重挡掉 | 尝试搬运 | 实际搬运 |
| :--- | ---: | ---: | ---: | ---: |
| 14:49:38～14:51:18（7 窗口）| 180～201 | **0** | 19.0～21.3 MB | 同左（**一次没挡掉**）|
| 14:58:47～15:00:07（9 窗口，**加了节流后**）| 585～597 | **540～551** | 61.9～63.1 MB | **4.76～4.97 MB** |

⇒ ⭐ **`setItem` ≈ 591 / 10 秒 = 59.1 次/秒 ≈ 逐帧（60fps）** ⇒ **报告的"逐帧写存档"是对的**，
我此前"高估 8 倍"的结论**只适用于那个场景**，在此更正。

⇒ ⭐ 而且**去重在花园里完全无效**（每个窗口都是 0）：因为 `grownTime` / `waterCD` 这类浮点每帧都在变，
**每次写的都是新值** ⇒ "值未变则跳过"永远不成立。

## 真正有效的手段：按 key **节流合并**

每个键最多每 **200ms** 镜像一次，期间只保留**最新值**（`MIRROR_MIN_INTERVAL_MS`）：

```
实际镜像 / 尝试  =  ~46 / 591  ≈ 7.8%      ⇒ ⭐ 挡掉 92.2%
跨进程搬运        =  6.2 MB/s → 0.49 MB/s  ⇒ ⭐ 降低 92%
```

**为什么这样是安全的**：游戏的真状态在 `localStorage` 里**已同步写好**（镜像只为跨重启持久化，读路径不受影响）；
而 ArkTS 侧的磁盘写本来就按 **400ms/1500ms** 去抖 ⇒ 比 200ms 更密的跨进程搬运**必然只是覆盖同一个待写值**。
⇒ 只丢"最后 200ms 的中间态"，而磁盘写本来也要等 400ms 以上。

**补发**：`pagehide` 与 `visibilitychange(hidden)` 时调用 `flushMirrorAll()` 把待发值全部发出
（ArkTS 侧 `onPageHide` 的 `flushNow` 只刷"已 put 的"，管不了 JS 侧还在待发的）。

**契约测试**（现共 11 条，全绿）：⑨ 同值只镜像一次｜⑩ 节流窗口内同键连写不同值只镜像一次且取最新值｜
⑪ `visibilitychange(hidden)` 必须把待发刷出去。

# 用户实测结果（最重要的那条证据）

当日全部改动落地后，用户反馈：**花园从 20~30 帧提升到 80+ 帧，且"很多场景都变流畅了"**。

⚠️ **归因要谨慎**：当天同时落地了多项改动（删除 LRU 缓存整条路径 / 镜像去重+节流 / 触摸层修正 /
move 按帧合并 / 删死代码），**无法把帧率提升单独归给哪一项**。但有一点是明确的：

> ⭐ **花园正是镜像最密集的场景**（实测 59 次/秒、每次约 107KB ⇒ 尝试流量 6.2 MB/s），
> 而节流把它压到 **0.49 MB/s（−92%）**。

⇒ 这解释了为什么**平均 CPU 看不出大变化、帧率却提升明显**：
这类成本的伤害主要在**帧时间尖峰（GC / 跨进程搬运抖动）**，不在平均占用。
**教训：评估这类改动要看 fps / 帧时间，不要只看平均 CPU。**
