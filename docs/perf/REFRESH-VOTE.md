# 期望刷新率投票：在这台手机上**纯成本、零收益**（三点实测 + 系统读数）

> 日期：2026-10-07 ｜ 设备：HUAWEI Mate 60（BRA-AL00 型号，phone，API 26）
> 背景：性能审查报告附录 A 把 `displaySync` 逐帧刷新率投票列为掉帧**次因**，但注明"这是权衡，不是纯负，别单独当结论"。
> 本文用**三点 CPU 实测 + 系统侧读数**把它测清楚了。

## 被测机制

`services/RefreshVote.ets` + `Index.ets`：注册每 vsync 触发的空回调参与刷新率投票，
默认「期望刷新率 = 120」(见 `ShellPrefs.PREF_EXPECTED_REFRESH`，可在壳层设置面板改)。

## 方法

同一台设备、同一场景（花园）、同一构建，只改这一项设置，每次**静止**测 60 秒：
`hdc -t <sn> shell "top -b -n 1 -p <pid>"` 取 `TIME+`（累计 CPU 时间）⇒ **Δ ÷ 60 = 平均占用核数**。
设置值**从设备 Preferences 里读**（`expected_refresh`），不靠人工确认。

## 结果（三点，控制场景漂移）

| # | 「期望刷新率」| 设备上实测值 | Δ CPU / 60 s | 平均占用 |
| :--- | :--- | :--- | ---: | ---: |
| ① | 120（默认）| `120` | 57.69 s | **0.962 核** |
| ② | 关闭 | `off` | 49.55 s | **0.826 核** |
| ③ | 120（改回）| `120` | 54.44 s | **0.907 核** |

- 开：0.962 / 0.907 ⇒ 均值 **0.934**，组内极差 **0.055**
- 关：**0.826**
- ⇒ 差 **≈0.108 个核 = −11.6%**，**差值约为组内波动的 2 倍** ⇒ 是真实效应，但**温和**
  （远不是报告暗示的那种量级）。

## ⭐ 决定性的一条：系统说它没生效

投票开着（`expected_refresh=120`）、应用在**前台**、人在**花园**时，读系统屏幕信息：

```
hidumper -s RenderService -a screen
screen[0]: ... skipFrameInterval=1, expectedRefreshRate=-1, skipFrameStrategy=0
supportedMode[0]: 1216x2688, refreshRate=120
supportedMode[1]: 1216x2688, refreshRate=90
supportedMode[2]: 1216x2688, refreshRate=60
```

**`expectedRefreshRate = -1`** = 系统侧**没有期望刷新率** ⇒ 我们投的 120 **没有被采纳**。

⇒ 也就是说在这台手机上：**花掉 ≈0.108 个核，换回"什么也没发生"**。

这与更早那轮的实测结论一致（当时记为「本机系统策略不接受该声明：**平板有效，手机 BRA-AL00 无效**」），
现在它同时有了**客观读数**（系统字段）与**量化代价**（三点 CPU）。

## 建议（按可接受度排序）

1. **保持现状 + 文档化**（最小动作）：默认仍为 120，用户可在面板里关；把这笔代价写进文档。
2. ⭐ **自适应**（推荐，但要小心）：投票前先 `setExpectedFrameRateRange`，
   随后读 `display.getDefaultDisplaySync().refreshRate`；
   若游戏运行中该值**没有被抬到期望值** ⇒ 判定"系统不采纳" ⇒ **停止逐 vsync 投票**。
   ⇒ 这样平板照常受益、这台手机自动省下 ~11% 进程 CPU，且**不需要用户懂设置**。
   ⚠️ 风险：idle 时刷新率本来就可能低于期望 ⇒ 必须**在渲染中**取样、并加迟滞，避免误判。
3. **按设备类型默认关**（简单粗糙）：phone 形态默认 `off`、平板默认 `120`。
   ⚠️ 但"手机不接受"是**本机型**的特性，未必适用于所有手机 ⇒ 比方案 2 差。
